## 执行摘要

Nexus 是面向个人开发者、Coding Agent 和小型技术团队的分布式工作空间。它将用户拥有或获准使用的设备、服务、执行环境与数据资源组织起来，使用户能够通过稳定的资源名称访问服务、提交任务并取得可信结果。

Nexus 的核心价值，是将跨设备操作中反复出现的连接、鉴权、环境选择、输入准备、任务执行和结果回收，组织成一套连续的使用体验。用户可以在 Windows 上编辑代码或运行 Agent，在 Linux 上构建和测试，调用另一台设备上的 GPU，并从同一工作空间查看任务、日志和产物。

产品提供三个相互依赖的能力层级：统一连接使设备之间具备可用的通信路径；统一资源访问使能力可以被命名、发现和授权使用；分布式工作空间使任务可以携带明确输入，在合适的环境中执行，并形成可追溯的结果。

Nexus 采用统一的 **Resource、Provider、Intent、Plan、Session** 核心模型，以 Workspace 组织身份、资源和策略，以 Task 记录具有明确目标与结果的工作。自动选择始终受权限、兼容性、数据位置和预算约束；用户可以查看选择依据，也可以在授权范围内指定执行位置。

N3 的首个完整交付场景是：**Windows 上的用户或 Agent 提交当前项目的一次构建或测试，可信 Linux 节点执行确定版本的输入，任务状态、日志、退出码和产物返回同一 Workspace。**多节点调度、共享缓存、GPU、浏览器入口及移动设备资源共享，围绕这一闭环逐步扩展。

## 1. 产品定位与价值

### 1.1 产品定义

Nexus 将分散的设备能力组织成可发现、可授权、可调用的资源，并管理资源使用的全过程。用户表达访问目标或任务要求，Nexus 完成资源匹配、访问检查、连接建立、执行准备、状态跟踪和结果交付。

用户面对的是一个统一的工作空间；具体工作仍在实际节点和运行环境中完成。操作系统、处理器架构、软件依赖、网络条件与数据位置等差异，通过资源能力和使用约束明确表达。

统一的含义是统一入口、身份、资源语义与操作反馈。任务是否可以跨节点执行、服务是否可以替换提供方、数据是否可以移动，均由其明确契约决定。

### 1.2 解决的问题

多设备开发的主要成本来自操作之间缺少连续性：服务名称与地址相互脱节，执行环境需要人工寻找，代码版本与测试结果难以对应，网络中断后任务状态不明，Agent 的工具能力受宿主机限制。

Nexus 将这些成本转化为可管理的产品能力：

| 用户问题 | Nexus 提供的能力 | 用户获得的结果 |
| --- | --- | --- |
| 设备地址和网络位置变化 | 稳定资源身份与路径管理 | 继续使用相同资源名称 |
| 本机缺少合适的开发环境 | 环境匹配与远程执行 | 在符合要求的节点完成工作 |
| 远端执行前需要手动整理文件 | 输入快照与受控数据传输 | 明确知道本次任务使用了什么输入 |
| 输出散落在不同机器 | 统一任务记录与产物管理 | 在同一入口取得结果 |
| Agent 需要人工协助使用远端能力 | 结构化资源与任务接口 | Agent 可以在授权范围内完成跨设备工作 |
| 网络或节点故障导致状态不明 | 持久任务记录、重新附着与状态核实 | 可以区分连接异常、执行失败与结果未知 |

### 1.3 主要价值主张

**连接已有设备，直接使用资源，在合适的环境中完成任务。**

对个人开发者，价值是减少环境重复配置和跨设备操作；对 Agent，价值是获得稳定、可授权的外部执行能力；对小型团队，价值是共享已有环境，并明确记录谁使用了什么资源、执行了什么工作。

## 2. 目标用户与核心场景

### 2.1 首要用户

首要用户是拥有两台及以上设备，或需要跨操作系统执行任务的开发者。典型环境包括 Windows 编辑端、Linux 构建节点、个人服务器和可选 GPU 设备。

Coding Agent 是一级调用主体。Agent 可以继续运行在用户现有工具中，通过 Nexus 调用远端环境；远端节点只需提供所需执行能力，无须同时运行相同的 Agent 产品。

小型技术团队是后续重点用户，主要需求包括共享构建环境、资源授权、任务追踪和成本控制。面向更大规模组织的治理能力，应在个人与小型 Workspace 的基础体验成立后扩展。

### 2.2 核心场景

| 场景 | 用户操作 | 产品交付 |
| --- | --- | --- |
| Windows 编辑，Linux 构建 | 对当前项目提交构建或测试 | 固定输入版本、选择 Linux 环境、执行并返回结果 |
| Agent 跨设备工作 | Agent 请求符合要求的执行环境 | 结构化任务状态、日志、诊断信息与产物 |
| 使用已有 GPU | 提交声明 GPU 与运行环境要求的任务 | 在兼容节点执行，并返回输出 |
| 访问开发服务 | 打开工作空间中的服务名称 | 完成身份检查与连接，进入可用服务 |
| 共享开发预览 | 为指定服务创建有时限的访问入口 | 受众、有效期和访问范围明确的链接 |
| 移动访问工作空间 | 手机在不同网络中访问资源或查看任务 | 保持资源身份和权限语义，按连接能力恢复访问 |

### 2.3 首次使用的价值时刻

用户在两台已具备兼容执行环境的设备加入 Workspace 后，能够完成一次跨设备任务，并在发起端看到对应输入、执行节点、日志、退出码和产物。

“五分钟获得首次结果”可作为已准备好环境下的体验目标。首次安装大型工具链、下载镜像、大规模传输项目以及外部网络不可用等情况，应独立展示进度与耗时。

## 3. 产品原则

1. **资源是主要操作对象。**用户通过资源名称表达目标；设备视图用于管理、诊断和必要的显式选择。
2. **自动化必须可解释。**系统说明选择哪个提供方、哪些条件影响选择，以及失败后有哪些可执行的处理方式。
3. **明确约束先于优化。**身份、权限、环境兼容性、数据范围和预算属于硬约束；速度、负载与缓存命中属于优化因素。
4. **优先利用已有资源。**在满足要求的前提下，综合考虑本地执行、数据位置、性能和成本；本地优先是一项默认偏好。
5. **任务结果必须可信。**记录输入版本、环境、实际执行位置和完成证据，区分执行结果、连接状态与产物交付状态。
6. **用户与 Agent 使用同一能力体系。**两者共享资源模型和执行语义，分别具有独立身份与权限。
7. **高级能力逐步显现。**日常操作保持直接，网络路径、调度因素和详细诊断在需要时展开。
8. **扩展遵循平台边界。**设备贡献何种能力，由其运行环境、系统权限、可用状态和所有者授权共同决定。

## 4. 统一产品模型

### 4.1 Workspace 与 Node

**Workspace 是资源组织、身份授权、策略管理和活动记录的作用域。**它包含成员、节点、资源、任务与相关数据；一个 Workspace 内部仍可以存在项目隔离、资源隔离和不同信任等级。

Workspace 与源码目录具有不同含义。一个 Workspace 可以管理多个项目；某个项目的源码、输入快照和构建产物，只是其中一部分资源。

**Node 是运行 Nexus 节点组件并具有独立身份的参与实体。**Node 可以消费资源，也可以在授权后承载 Provider；加入 Workspace 不会自动公开所有本地服务、文件和硬件。

浏览器可以作为访问入口，传输中继可以作为外部基础设施。是否属于 Workspace Node，取决于其是否经过节点注册并承担对应职责。

### 4.2 五个核心领域对象

| 对象 | 定义 | 产品职责 |
| --- | --- | --- |
| Resource，资源 | 具有稳定身份、使用接口和访问策略的逻辑对象 | 描述用户可以使用什么 |
| Provider，提供方 | 为资源实现约定接口的运行实例或适配实例 | 描述该能力当前由谁提供、如何提供 |
| Intent，意图 | 结构化的操作请求及其约束 | 描述本次要做什么、允许什么 |
| Plan，方案 | 经过校验的资源选择与操作安排 | 描述本次选择、准备步骤、预算与恢复规则 |
| Session，会话 | 某次实际资源使用的上下文 | 管理主体、权限、连接、租约与活动状态 |

这些对象通过关系协同工作：调用方在 Workspace 中提交 Intent；系统依据资源契约与策略选择 Provider，形成 Plan；被接受的方案通过一个或多个 Session 使用资源。

Node 是 Provider 的承载位置，两者分别管理。同一个 Node 可以承载多个 Provider；一个 Provider 也可以将已有服务或受管执行环境接入 Workspace。

### 4.3 任务与数据对象

**Task 是具有明确目标、状态与结果记录的工作单元。**构建、测试、转码和推理都可以形成 Task。Task 可以涉及多个 Session，也可以在控制连接断开后继续存在。

**Snapshot 是任务输入的固定版本。**它标识本次执行使用的文件和数据集合。

**Artifact 是任务产生并登记的输出。**可执行文件、测试报告、生成文件、模型输出和待应用补丁都可以成为 Artifact。

任务的一次重新执行应具有独立的尝试记录，使输入、执行位置、日志、外部影响与最终结果保持对应。

### 4.4 能力与资源的区别

CPU 架构、内存、GPU 型号、操作系统和工具链版本，通常是 Provider 的能力描述及调度条件。用户实际调用的资源可以是构建环境、GPU 执行环境或具体服务。

例如，`rust-build` 表达一个约定了操作接口和环境要求的构建资源；`linux`、`x86_64`、可用内存和 Rust 版本用于判断某个 Provider 是否能够完成请求。

### 4.5 多 Provider 的替换条件

同一资源可以由多个 Provider 提供，但可替换性必须由契约声明。环境兼容、数据版本、身份授权、所需状态和结果语义均满足要求时，系统才可以更换提供方。

多个构建节点可以共同提供同一种兼容构建环境；两个都开放数据库端口的节点，只有在其数据与一致性关系符合资源契约时，才可以成为同一资源的可替换提供方。

已有 Session 的提供方切换还需要会话恢复能力；新任务可以重新选择节点，并不意味着正在运行的进程可以透明迁移。

## 5. 完整用户体验

### 5.1 建立工作空间

用户创建或加入 Workspace，完成节点身份确认，选择设备允许提供的能力，并取得可见资源列表。已有环境经过能力检查后才能被标记为可执行；未配置完成的环境应展示缺失条件。

资源发布采用明确的授权流程。开发服务、项目目录、GPU、摄像头和麦克风等能力分别授权；敏感能力具有清晰的启用状态和停用入口。

### 5.2 使用资源

用户选择资源或提交任务要求。系统先检查权限与硬约束，再确定执行方案；在预先授权的范围内自动运行，需要扩大权限、公开访问或超出预算时，提供具体方案供用户决定。

对于常见操作，界面展示目标、执行位置、当前状态和结果。用户可以展开环境、输入、网络路径、预计成本与详细日志。

### 5.3 管理活动

统一 Activity 记录访问、执行、取消、结果交付和资源状态变化。任务记录能够回答：谁发起了工作、使用了哪些输入、在哪里运行、为何选择该节点、执行结果是什么，以及产物是否可以取得。

### 5.4 主要界面

| 入口 | 主要内容 |
| --- | --- |
| 概览 | 可用资源、进行中的任务、最近结果和需要处理的问题 |
| 资源 | 可访问服务、执行环境、数据与其他已授权能力 |
| 任务 | 执行进度、日志、尝试记录、取消操作与结果 |
| 设备 | 设备身份、在线状态、提供能力、共享开关与资源限制 |
| 活动 | 用户、Agent 与系统操作的统一时间线 |
| 设置 | 成员、策略、网络、存储、预算与部署配置 |

网络拓扑和传输细节属于可展开的诊断视图。故障提示应说明受影响的操作，并给出重连、补充环境、调整资源要求或联系资源所有者等实际处理入口。

## 6. 统一连接与网络能力

### 6.1 连接服务于资源使用

Nexus 为资源访问和任务执行提供可用通信路径。路径选择综合考虑可达性、身份验证、策略、质量与成本，可以使用局域网直连、公网直连、NAT 穿透和获准的中继等方式。

接入网络、地址族、路径组织与传输协议分别处理。某条路径可以同时使用局域网、IPv6 和 QUIC；中继路径也可以使用不同传输协议。用户无需在这些技术名词之间手动选择。

连接层向上提供可达状态、质量信息、失败原因与恢复事件；资源层据此判断能否执行，以及当前路径是否满足任务要求。

### 6.2 私有资源与互联网访问

Nexus 同时承载 Workspace 私有资源访问和按策略进行的互联网访问。在 Android 上，目标体验是通过统一的 VPN 入口管理这两类流量，避免用户为两种需求反复切换接管方式。

私有资源访问遵循 Workspace 权限；互联网流量根据用户配置选择直连或代理。DNS、IPv4、IPv6 和路径回退应遵循一致的策略。明确要求代理或受保护路径的流量，在对应路径失效时按配置阻断或回退，并向用户显示实际行为。

桌面端可以按需采用资源级连接或系统级网络接管，具体模式应在产品中明确呈现。

### 6.3 网络变化与恢复

设备切换网络后，资源身份、任务标识和权限保持稳定；系统尝试重新建立可用路径，并在协议及应用能力允许时恢复会话。

恢复能力分为连接恢复、会话重新附着、应用请求重试和任务重新执行。每一层分别定义语义与条件。已建立的任意应用连接、公开访问出口和远端进程，都不能仅凭“自动选路”获得透明迁移能力。

直连失败时可以选择已配置、获授权且具有可用容量的中继；没有可用路径时，资源应显示为不可达并给出原因。

### 6.4 Network Boost

Network Boost 是可选增强能力，包括基于观测的路径选择、流量优先级、发送节奏控制，以及在适用条件下使用多路径或冗余传输。

其效果通过任务完成时间、交互延迟、抖动和额外资源消耗评估。系统明确区分自身可控制的队列与端到端观测；对共享接入链路和外部网络，只能在实际控制能力内改善体验。

需要额外流量、电量、中继费用或出口变化的策略，必须受用户预算和预先授权约束。资源访问的正确性与权限检查不依赖 Network Boost 是否开启。

## 7. 资源发现与访问

### 7.1 资源目录

资源目录提供稳定标识、可读名称、资源类型、使用接口、权限、提供方和有效的可用状态。用户只看到其有权发现的资源；可发现与可使用分别授权。

资源健康、节点在线和执行容量分别表达。节点在线不等于某项工具链可用，资源已注册不等于当前仍可接受新任务。过期的能力信息和健康信息不能继续被当作有效的调度依据。

### 7.2 资源类别

| 类别 | 典型资源 | 使用方式 |
| --- | --- | --- |
| 服务 | Web 应用、SSH、API、数据库端点 | 打开、连接或通过受控入口访问 |
| 执行环境 | 构建、测试、推理、转码环境 | 提交具有输入、约束和结果要求的任务 |
| 数据 | 项目快照、文件集合、产物存储、缓存 | 在明确的数据范围和版本规则下读取或写入 |
| 工具与运行时 | 浏览器工具、容器执行适配、Agent Runtime | 调用其公开的受控接口 |
| 设备能力 | 经授权的摄像头、传感器和其他外设 | 使用设备声明且平台允许的接口 |

不同资源共用身份、授权和活动记录；具体协议、数据一致性和生命周期由资源类型契约定义。

### 7.3 浏览器访问与资源发布

浏览器入口提供资源列表、任务管理、日志、产物下载，以及适配后的 Web 服务或终端。需要访问普通 TCP、SSH 或其他原生协议时，由明确配置的网关或适配服务承担转换。

资源发布具有三种明确范围：Workspace 内部、指定外部受众和公开访问。默认使用 Workspace 内部范围；外部发布要求明确指定资源、访问范围、有效期和可用的身份检查方式。

发布入口必须能够撤销，并显示其当前生效状态。兼容 WebSocket、Cookie、重定向和认证流程的能力，应按服务类型验证后声明。

浏览器和网关之间、网关和目标资源之间的信任边界应分别呈现；在网关终止加密或处理明文的访问方式，需要将网关纳入信任范围。

## 8. 计算、构建与运行环境

### 8.1 执行契约

一次执行请求应具有明确的命令或操作、输入、环境要求、工作目录、资源限制、超时、输出要求和副作用声明。具有可用默认值的字段可以由项目配置补齐，系统应保留最终生效的执行契约。

兼容的执行环境可以来自原生工具链、容器或其他受管运行环境。Nexus 负责选择和调用已支持的环境；环境供应与安装可以通过独立的适配能力完成。

### 8.2 输入与环境可追溯

任务开始前固定输入版本，执行期间本地后续修改不会改变该任务已经确认的输入。输入可以包含未提交修改，以及用户明确纳入的未跟踪文件。

任务记录应保存环境标识与关键版本。固定镜像和依赖有助于提高可复现性；依赖宿主环境或外部在线服务的执行，则应记录其实际条件与复现限制。

跨平台任务需要明确处理架构、路径、大小写、权限、符号链接和依赖兼容性。不满足要求时，应拒绝执行或选择符合条件的环境。

### 8.3 提供方选择

选择过程先过滤硬约束，再比较优化因素。

| 硬约束 | 优化因素 |
| --- | --- |
| 用户与 Agent 权限 | 预计总完成时间 |
| 节点与环境信任要求 | 输入、依赖与缓存的数据位置 |
| 操作系统、架构、运行时与工具链 | 当前负载与等待时间 |
| GPU 类型、可用内存和所需容量 | 网络质量与传输开销 |
| 数据出域、网络访问与密钥使用策略 | 电量、温度、设备空闲情况 |
| 费用预算、截止时间与设备共享限制 | 用户偏好与已有执行历史 |

预计总完成时间应包含排队、环境准备、输入传输、执行和产物回收。数据不足时使用明确的默认规则，并标注估计的局限。

用户可以指定节点或 Provider；显式选择仍需通过权限和兼容性检查。条件不满足时，系统说明原因，只有在请求允许的范围内才改选其他提供方。

### 8.4 容量与副作用

Provider 接受任务时必须确认实际容量，并为已接受工作保留所需配额，避免单纯依赖旧的负载信息超额调度。新任务受到 CPU、内存、GPU、存储、并发和时间限制。

一般程序可以读写数据、访问网络或触发外部操作；执行权限必须与运行隔离和资源权限共同实施。具有部署、支付、删除或其他外部副作用的任务，按其声明的操作策略处理重试和确认。

### 8.5 GPU 与 Agent Runtime

GPU 能力以兼容的远端工作负载形式使用，例如推理、转码、渲染和 GPU 构建。驱动、框架、模型与输入条件都属于匹配范围；程序在实际 GPU 节点运行，返回其约定输出。

Agent Runtime 可以作为一种可选资源，供用户启动具有明确权限和生命周期的 Agent 工作。Agent 规划与推理的具体实现由相应运行时提供，Nexus 负责资源访问、执行承载和活动记录。

## 9. 项目数据、快照、产物与缓存

### 9.1 数据准备

项目配置明确输入根目录、包含与排除规则、依赖来源和输出范围。用户能够预览将传输的数据；密钥、凭据和与任务无关的私人文件采用独立的授权及注入机制。

数据准备支持按内容复用已存在的数据，减少重复传输。无法获得所需输入时，任务停留在准备阶段或返回明确错误；缺失输入不能被静默忽略。

### 9.2 写入与结果回收

执行默认使用隔离的工作目录。输出以 Artifact、补丁或明确的持久数据操作返回。

修改本地源码需要应用结果到指定基线；本地已有新修改时，应检测冲突并保留双方内容。长期共享可写目录属于单独声明的资源模式，其并发写入和一致性规则必须明确。

Nexus 首期通过输入快照、传输和产物回收完成任务数据闭环。按需挂载、工作集预取和更广泛的文件访问，可以作为后续数据 Provider 扩展。

### 9.3 产物管理

Artifact 记录来源任务、输入版本、执行环境、内容校验信息、访问权限、存储位置和保留期限。

命令执行完成与结果交付分别记录。如果任务契约要求生成并发布某个产物，只有该产物已登记且可以按约定访问时，才满足整体成功条件。产物上传失败应允许在条件恢复后补交，无须自动重新执行已经产生副作用的命令。

清理策略应尊重保留期、正在运行的任务和明确的引用关系。空间不足时，系统给出可理解的处理选择。

### 9.4 缓存

构建、依赖、镜像和产物缓存可以通过适配方式接入。缓存复用必须包含足以区分输入、工具链、目标平台、配置和信任域的条件，并验证内容完整性。

缓存命中用于优化性能；缓存缺失、失效或不可访问时，应回退到正确执行路径。跨用户或跨 Workspace 共享缓存必须受数据隔离与信任策略约束。

## 10. 人与 Agent 的统一接口

### 10.1 接口层次

图形界面、CLI 和结构化 API 共享同一资源模型、权限检查和任务状态。用户可以从任意入口查看同一任务，Agent 也可以在断开后根据任务标识恢复跟踪。

结构化 API 至少覆盖资源发现、操作校验、任务提交、任务查询、日志读取、取消请求、产物获取与服务访问。需要预览的操作应能返回具体 Plan，供调用方在授权流程中使用。

### 10.2 Intent 的确定含义

Intent 是结构化、可校验的操作请求。自然语言可以由上层界面或 Agent 转换为 Intent；权限、资源资格、预算与执行规则由可审计的策略机制执行。

接口返回明确的状态、错误类别和后续动作。对同一请求的重复提交，可以通过具有作用域和有效期的幂等键返回已有任务记录；外部系统产生的副作用仍需要对应操作自身提供去重或幂等能力。

### 10.3 Agent 权限

Agent 具有独立身份与受限凭据，权限可以限定到 Workspace、项目、资源、操作、数据范围、费用和时间。

“允许运行构建”需要配套限制构建环境可以访问的主机文件、网络、密钥和系统能力；运行来自项目的任意代码，应使用与其信任程度相匹配的隔离方式。

Agent 委托其他工具或运行时执行操作时，权限只能在既有授权内收缩。所有结果保留实际发起主体与执行主体，便于审计和故障定位。

## 11. 任务生命周期与可靠性

### 11.1 可恢复的任务记录

接受任务后，Nexus 返回稳定任务标识，并按约定持久保存执行契约与状态。批处理任务默认可以独立于发起端界面存在；交互式会话则明确声明连接断开后的处理策略。

网络连接、Session、Task 和产物交付分别跟踪。客户端断开可以导致暂时无法观测任务，远端任务是否继续运行由执行策略与当前状态决定。

### 11.2 状态语义

| 状态 | 对用户的含义 |
| --- | --- |
| 等待 | 请求已接受，正在等待可用资源或执行条件 |
| 准备 | 正在准备环境、输入和访问凭据 |
| 运行 | 执行端已确认任务开始，当前仍处于执行阶段 |
| 结果整理 | 已获得执行结果，正在登记日志与约定产物 |
| 成功 | 已满足任务契约定义的成功条件，结果已确认 |
| 失败 | 已确认执行或交付未满足任务契约，具有明确原因 |
| 已取消 | 已确认执行停止，或已确认任务没有开始执行 |
| 状态待核实 | 证据不足，暂时不能确定任务是否在运行或如何结束 |

取消请求作为独立标记显示，在确认停止之前不会提前显示“已取消”。状态待核实的任务应通过执行端记录和后续通信恢复核实，不能因一次请求超时就自动重新执行。

### 11.3 重试与重新执行

系统分别处理连接重试、日志续读、产物补传和任务重新执行。前几项通常可以在原任务上下文中恢复；任务重新执行则需要明确的安全条件。

每次重新执行保留独立尝试记录。对于可安全重试的任务，策略可以允许自动重试；对于执行结果未知或存在不可重复副作用的任务，先核实状态，再依照已授权策略处理。

发布版本必须声明其任务提交去重范围、状态保留期限、执行重试条件和异常恢复行为。任意程序的外部副作用不能仅依靠任务标识获得通用的“恰好执行一次”保证。

### 11.4 取消、超时与节点离线

执行超时、等待超时与网络请求超时分别生效。取消请求应传递到执行端，并按运行环境能力终止工作、回收配额和整理已有结果。

执行节点离线时，界面如实展示无法确认的状态。权限撤销和取消在不可达节点上不能被宣称为立即完成；通过短期授权、执行租约和恢复后的核实限制影响范围。

## 12. 身份、权限与信任

### 12.1 授权对象

Workspace 分别管理用户、Agent、节点与服务身份。授权覆盖资源发现、连接、执行、数据访问、资源发布、费用使用和管理操作。

加入 Workspace 表示身份获得了某些成员资格；具体能查看什么、使用什么、提供什么，仍由策略决定。提供方执行操作时必须再次校验有效授权，不能只依赖目录返回的结果。

### 12.2 双向信任

选择 Provider 时，需要判断该节点是否适合接触任务数据和凭据；接受任务时，也需要判断代码和调用方可以获得何种主机能力。

普通执行环境中的节点管理者可能接触任务数据。未经额外验证的隔离或保密计算能力，不能被当作允许将敏感数据发送给不可信节点的依据。

节点标签用于辅助策略表达，实际信任来自身份来源、管理关系、运行隔离与明确授权。

### 12.3 凭据与审计

任务凭据按用途、提供方和有效期发放，尽量在执行时注入。凭据不得成为普通项目快照、共享缓存或日志的一部分。

审计记录包含主体、资源、操作、授权依据和结果；日志内容、命令参数及其保留范围需要考虑敏感信息。用户可以查看并管理自己的执行历史与数据保留设置。

### 12.4 外部访问

公开或定向分享服务时，系统明确展示目标资源、入口、访问受众、有效期与限制条件。分享权限与资源使用权限分别管理，撤销后的传播范围和生效状态应可观察。

纯传输 Relay 只承担获准的转发职责，不因转发数据自动获得 Workspace 成员身份或资源执行权限。需要解密、认证代理或内容适配的网关具有更高信任要求，应明确声明。

## 13. 部署、管理与数据控制

### 13.1 部署模式

Nexus 支持以用户拥有的设备构建 Workspace，并允许接入经授权的服务器和云端环境。发现、协调、网关和中继可以根据部署模式使用自建或受托管服务。

控制服务负责成员、目录与策略等信息；任务数据通过选定的执行和传输路径流转。是否需要经过托管基础设施，以及相关数据可见性、费用与保留规则，应在部署配置中明确。

### 13.2 控制信息与可用性

每个 Workspace 必须具有明确的成员与策略权威来源。可以将控制服务部署在一个受信节点，也可以使用受管服务；多副本模式必须明确写入权威、版本冲突与故障恢复规则。

控制服务暂时不可达时，只能在有效的缓存授权、凭据和执行策略范围内继续工作。缓存到期或缺少授权依据的操作，应停止接受或等待恢复。

### 13.3 导出、迁移与撤销

Workspace 配置、资源定义和必要元数据应支持备份与迁移。数据、凭据和节点身份分别处理；迁移到新节点时，按其安全性质恢复或重新发放身份，避免产生无法区分的身份副本。

用户可以停止资源共享、移除节点、撤销凭据、清理缓存和导出任务记录。操作应说明对正在运行任务、既有会话和数据保留的影响。

### 13.4 成本控制

系统分别展示计算使用、存储、中继和数据传输等可计量成本。使用收费资源、开启高流量传输策略或创建额外云资源，需要处于用户已授权的预算范围内。

调度比较整个任务的预计代价，包括排队、准备、传输、执行和结果回收。预算不足时返回可执行的选择；已授权自动化可以在明确上限内继续工作。

## 14. 平台与设备角色

以下为目标能力分工；各发布版本按实际验证范围声明支持情况。

| 平台 | 主要角色 | 能力边界 |
| --- | --- | --- |
| Linux | 完整节点、构建与执行 Provider、网关或控制服务 | 按已安装运行时、权限和资源限制提供能力 |
| Windows | 开发入口、完整节点、原生执行 Provider | Linux 任务由兼容环境或远端 Linux Provider 承担 |
| macOS | 开发入口、完整节点、对应平台执行 Provider | 按平台、架构与工具链要求匹配任务 |
| Android | 统一网络入口、资源消费者、可选临时 Provider | 资源共享受授权、后台运行、电量、温度和网络条件约束 |
| iOS / iPadOS | 后续扩展的资源消费与网络入口 | 能力以系统允许的网络扩展和应用生命周期为边界 |
| 浏览器 | 无需原生安装的受限访问与任务管理入口 | 原生协议通过适配入口使用；可用能力由浏览器接口与服务端支持共同决定 |

### 14.1 Android 的默认行为

Android 首先满足持续使用的统一网络与 Workspace 访问需求。计算、外设、额外存储和中继贡献分别开启；默认不分享计算能力、不充当中继、不开放摄像头或麦克风。

用户开启临时计算后，可以设定充电、Wi-Fi、电量、温度、并发和工作时段等条件。节点只接受其架构与运行时兼容的任务，并允许在条件变化时按契约拒绝新任务、请求暂停或结束已有任务。

适合移动设备的工作应以实际收益验证，包括输入体积、传输时间、能耗和完成时间。手机算力的产品价值取决于具体工作负载及其运行条件。

### 14.2 持续可用与临时贡献

稳定服务器、桌面工作站和临时移动节点具有不同的可用性类别。需要长时间运行、持久状态或严格完成时限的任务，应选择满足相应可用性要求的 Provider。

| 领域 | Nexus 的责任 | 集成方式与边界 |

| 数据 | 输入版本、受控传输、产物与缓存访问 | 版本控制和底层存储通过适配接口接入 |

扩展必须说明自己提供的接口、所需权限、数据访问、故障行为和版本兼容性。未经验证的扩展不得自动提升为受信的执行或数据提供方。

Nexus 的产品规模由完整使用场景推动。新增资源类型应明确带来的用户收益，以及对权限、执行、数据和恢复语义的影响。

## 16. 分层交付与首期范围

### 16.1 三个能力层级

| 层级 | 产品问题 | 完成标志 |
| --- | --- | --- |
| N1：Universal Connectivity | 已授权设备如何稳定通信，同时保持所需互联网访问？ | 支持的网络条件下，直连与回退路径可验证，失败与恢复可观察 |
| N2：Universal Resource Access | 用户如何按资源名称访问设备能力？ | 资源具有稳定身份，发现、授权、访问和撤销构成完整闭环 |
| N3：Distributed Workspace | 用户如何使用多个节点完成一次工作并取得可信结果？ | 输入、环境、执行、状态与产物形成可追溯的任务闭环 |

三个层级共同构成 Nexus。N3 的交付建立在所需连接与资源权限已经可用的基础上；网络层和资源层的改进继续服务于整个工作空间。

### 16.2 N3 首期必须交付

首期面向个人开发者，完整支持 Windows 用户或 Agent 调用可信 Linux 环境完成构建与测试。

必需范围包括：Workspace 与节点注册；资源能力检查与发布；指定资源或节点执行；固定项目输入；环境兼容性校验；隔离执行与配额；持久任务标识；状态、日志与退出码；产物回收；取消、超时和状态核实；CLI 与结构化 API 的一致行为。

首期调度可以使用明确默认 Provider 和受约束的简单选择规则。实际多节点使用形成后，再增加自动评估、容量协调和历史性能优化。

## 17. 产品验收与成功指标

### 17.1 功能验收

| 验收场景 | 必须观察到的结果 |
| --- | --- |
| Windows 提交当前代码到 Linux 测试 | 结果对应明确输入版本，环境、节点、日志和退出码可以追溯 |
| 提交后继续在本地修改 | 运行中的任务输入保持已确认版本，新修改用于后续任务 |
| 执行中关闭客户端后重新打开 | 根据任务标识恢复查询和日志读取，任务策略得到遵守 |
| 直连不可用但有获准中继 | 使用可用回退路径，界面显示实际状态与额外成本 |
| 运行时网络断开 | 区分连接故障与任务状态，执行结果未知时不擅自重复执行 |
| 重复提交同一请求 | 在声明的幂等范围内返回同一任务，不创建无意的重复工作 |
| 取消时执行节点不可达 | 显示取消待确认及当前已知状态，恢复后核实结果 |
| 命令完成但产物上传中断 | 保留执行结果，明确交付未完成，并支持按规则继续回收 |
| 不同环境或平台不兼容 | 拒绝执行或使用获准且兼容的 Provider，并说明选择依据 |
| Agent 请求越权资源或公开发布 | 操作被执行侧拒绝并留下清晰记录 |
| 手机未授权共享计算 | 不接收计算任务；开启后的条件限制得到执行 |

### 17.2 衡量真实价值

首要指标是 **每个活跃 Workspace 持续完成的有效跨设备任务数**，并观察用户是否在日常工作中主动重复使用。有效任务必须具有确定的输入、已核实的执行结局和按契约可取得的结果。

测试命令返回非零退出码，可能是一次成功交付的测试结果。因此产品可靠性和用户工作负载成功率分别统计。

| 指标 | 定义与用途 |
| --- | --- |
| 首次可信结果时间 | 从满足基本接入条件到取得首个可追溯结果的时间，分别记录安装和数据准备成本 |
| 结果确认率 | 在约定观察窗口内能够确认执行结局的已接受任务比例 |
| 结果交付率 | 已形成约定输出的任务中，结果可按权限实际取得的比例 |
| 状态待核实时长 | 从失去有效状态到重新确认任务结局的时间 |
| 人工干预次数 | 完成一次日常跨设备任务所需的人工准备与恢复操作次数 |
| 任务总完成时间 | 排队、准备、传输、执行和回收的总时间，并分别分析各部分 |
| 资源复用收益 | 与相同输入和环境条件下的基线比较，衡量环境复用、缓存和调度带来的收益 |
| 额外资源成本 | 网络流量、耗电、存储、中继和付费计算的实际消耗 |

性能目标和服务等级必须注明平台、部署模式、网络条件、工作负载、样本范围与统计口径。发布验收以真实场景和可重复测试为依据。

## 18. 产品长期形态

Nexus 的长期形态，是连接用户工具与其计算环境的持续运行基础设施。应用、开发工具和 Agent 使用同一套资源接口；用户自己的设备、团队环境及获准云资源通过统一契约提供能力。

随着资源类型增加，用户可以在工作空间中完成更丰富的任务组合，仍然保持一致的身份、授权、输入、执行、结果与活动记录。

产品价值最终体现在日常行为中：用户能够自然地把工作提交给自己的 Workspace，并清楚知道任务在哪里执行、使用了什么数据、是否完成，以及结果在哪里。

**Nexus Distributed Workspace：让已有的设备与资源，成为一个可以持续使用、明确授权、可靠执行和追溯结果的工作空间。**

## 附录 A：标准使用示例

以下示例定义交互方向，命令语法与 API 字段由具体版本的接口规范确定。

### A.1 在构建资源中运行测试

```bash
nexus run --resource rust-build --project . -- cargo test --workspace
```

用户选择项目与构建资源，系统固定本次输入、选择符合契约的 Provider，并返回任务标识。退出码、日志和约定产物关联到同一次任务尝试。

### A.2 指定执行节点

```bash
nexus run --resource rust-build --on linux-build --project . -- cargo test --workspace
```

目标节点仍需满足权限、环境与容量要求；执行位置发生变化需要符合本次请求允许的回退策略。

### A.3 查看任务与请求取消

```bash
nexus task show task-123
nexus task logs task-123 --follow
nexus task cancel task-123
```

任务查询和日志读取可以重新建立；取消命令返回请求状态，最终停止状态以执行端确认为准。

### A.4 打开与发布服务

```bash
nexus open dev-web
nexus expose dev-web --audience workspace
```

默认保持 Workspace 访问范围。对外分享通过独立选项或界面明确受众、有效期和访问限制。

### A.5 Agent 的结构化执行请求

```json
{
  "workspace": "personal",
  "resource": "rust-build",
  "operation": "execute",
  "input_snapshot": "snapshot-456",
  "command": ["cargo", "test", "--workspace"],
  "requirements": {
    "os": "linux",
    "architecture": "x86_64",
    "environment": "rust-project-a-locked"
  },
  "limits": {
    "timeout_seconds": 1200
  },
  "idempotency_key": "request-789"
}
```

系统返回任务标识、已接受的执行契约与当前状态；Provider、Session、尝试记录和 Artifact 按实际生命周期逐步关联。请求中的环境标识必须解析到可验证的环境定义，不能仅以名称宣称环境已被固定。

## 附录 B：术语表

| 术语 | 本文含义 |
| --- | --- |
| Workspace | 组织资源、身份、策略和活动的工作空间 |
| Node | 具有节点身份并运行相应 Nexus 组件的参与实体 |
| Resource | 具有稳定身份、接口和访问策略的逻辑资源 |
| Capability | 用于描述兼容性、容量及功能条件的能力属性 |
| Provider | 实现资源使用接口的运行实例或适配实例 |
| Intent | 本次操作的结构化请求及约束 |
| Plan | 经过校验的资源选择、准备与执行安排 |
| Session | 某次实际资源使用的上下文 |
| Task | 具有明确目标和可追溯结果的工作单元 |
| Project | Workspace 中被管理或用于执行的一组项目内容 |
| Snapshot | 本次执行已经固定的输入版本 |
| Artifact | 任务产生并登记管理的输出 |
| Gateway | 提供入口、协议适配或访问代理的受信组件 |
| Relay | 承担传输转发职责的中继组件 |
| Network Boost | 在策略与预算内改善网络体验的可选能力 |
