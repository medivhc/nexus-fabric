# Nexus 地基设计：自由、高速的节点互联网络

| 文档属性 | 内容 |
| --- | --- |
| 版本 | 0.1（草案） |
| 日期 | 2026-09-30 |
| 定位 | N1（Universal Connectivity）地基的架构设计，白皮书终局设想的下层实现 |
| 状态 | 讨论稿：核心分层与方向已对齐，§11 留有待决策事项 |
| 前置阅读 | `docs/vision-realignment/PROPOSAL.md`、白皮书《Nexus Distributed Workspace 产品白皮书》 |

**一句话：** 地基是一套"自由、高速、节点互联"的网络 substrate。上层模块（分布式工作空间、分布式文件系统等）通过 QUIC-like API 调用它，不直接面对直连 / TURN / 代理这些路径细节。

---

## 1. 定位与边界

### 1.1 地基 vs 上层

```
┌─────────────────────────────────────────────┐
│ 上层：分布式工作空间 / 分布式文件系统 / …      │  ← 白皮书 N2/N3，调用地基
├─────────────────────────────────────────────┤
│ 地基：自由、高速、节点互联的网络 substrate     │  ← 本文档，N1
└─────────────────────────────────────────────┘
```

- **地基的承诺**：任意两个节点之间"默认自由高速"——自动穿越封锁、自动选最优路径、网络切换不断连。
- **上层的视角**：只看到"可靠流 / 不可靠数据报 / 统计信息"，不感知底层是直连还是 TURN 还是代理。
- **与白皮书的关系**：白皮书是终局设想（N1/N2/N3），本文是 N1 的实现设计。N2/N3 的 Workspace/Compute 语义在地基之上构建。

### 1.2 "自由高速"的含义

- **自由**：解决网络封锁——流量能按策略走代理出口，混淆手段可热插拔（见 §7）。
- **高速**：节点互联走直连（NAT 穿透）；直连不可用时 TURN 中继；多路径并发、按优先级调度（见 §4）。
- **默认**：用户不配置也能用，策略以自动为主、手动为 override（见 §5）。

### 1.3 非目标

- 地基不做 Workspace 语义（成员、任务、产物）——那是 N2/N3。
- 地基不替应用做业务逻辑——只提供传输语义。
- 首期不做完整 MPQUIC——多路径先做简化版（见 §4.6）。

## 2. 分层架构

```
应用（无需修改，使用标准 socket API）
  │
  ▼
┌─────────────────────────────────────────────────┐
│ 投影层 Projection（§6）                           │
│  · TUN 透明捕获 → 进程归因 → 优先级标记             │
│  · SOCKS5 / HTTP 语义入口                         │
│  输出：可靠流 / 不可靠数据报 + 元数据               │
│       （进程、优先级类、语义标签如目标 host）        │
├─────────────────────────────────────────────────┤
│ Fabric 会话层 Session（§3，QUIC-like）              │
│  · Connection ID 与五元组解耦                      │
│  · 可靠流：有序、重传、流量控制                     │
│  · 不可靠数据报：尽力而为、低延迟                   │
│  · 统计：per-path RTT/丢包/吞吐、当前活跃路径       │
├─────────────────────────────────────────────────┤
│ 路径层 Path（§4）                                  │
│  · 候选：直连（NAT 穿透）→ TURN → 代理出口          │
│  · 探测、打分、竞速、切换、粘性、质量预测            │
├─────────────────────────────────────────────────┤
│ 物理传输：UDP 为主，TCP 兜底                        │
└─────────────────────────────────────────────────┘
```

**层间契约**：上层只依赖会话层 API；会话层只依赖路径层的"给我一条到对端的逻辑通道"；路径层只依赖物理传输的收发包能力。每层可独立演进、独立测试。

## 3. Fabric 会话层：QUIC-like API

### 3.1 设计原则

语义对标 QUIC，线协议自己设计（clean-room）。不直接采用 `quinn` 的决定待定（见 §11），但 API 形状先行冻结——上层模块和传输实现都依赖它。

### 3.2 API 形状（草案）

```rust
// 连接：以对端身份（公钥）为标识，与 IP/端口解耦
struct Connection {
    peer: PeerId,            // ed25519 公钥，见 §8
    id: ConnectionId,        // 逻辑连接标识，用于漫游后识别
}

// 可靠流：文件传输、RPC、workspace 同步
trait ReliableStream {
    async fn write(&mut self, buf: &[u8]) -> Result<()>;
    async fn read(&mut self, buf: &mut [u8]) -> Result<usize>;
    // 有序、重传、流量控制、拥塞控制
}

// 不可靠数据报：实时媒体、心跳、探测
trait Unreliable {
    fn send_datagram(&self, data: &[u8]) -> Result<()>;  // 尽力而为
    async fn recv_datagram(&self) -> Result<Vec<u8>>;
}

// 统计：给路径层做决策，也给上层/用户做诊断
struct Stats {
    per_path: Vec<PathStats>,   // 每条候选路径
    active_path: PathId,
    // PathStats { rtt_ms, loss_rate, throughput_bps, ... }
}
```

### 3.3 核心机制

| 机制 | 说明 |
| --- | --- |
| Connection ID | 连接身份与五元组解耦，是"WiFi 关不断传"的基础。地址变化后凭 CID 重认连接 |
| 加密 | 全程加密（TLS 1.3 语义），中继/TURN 看不见内容 |
| ACK/重传 | 可靠流的确认与重传，包序号空间独立于路径 |
| 路径迁移 | 地址变化时做路径验证（challenge/response）后迁移，未确认数据在新路径重传 |
| 0-RTT | 已知对端可快速重建（远期） |

### 3.4 与 QUIC 的关系：`quinn-proto` + 自写驱动，保留加密

- **传输底座**：`quinn-proto`（quinn 0.11 的 sans-IO 核心）+ 自写 std 驱动（UDP socket + 定时器轮 + poll 循环）。
  不用高层 `quinn`（会引入 tokio，仓库零 tokio，这是架构级决定）；不用 `quiche`
 （BoringSSL 硬耦合：cmake/C++ 构建、Windows 需 NASM、Cloudflare 拒绝 rustls 后端，
  与 supply-chain 纪律冲突）；不用 iroh 的 fork（避免跟随其发布节奏）。
- sans-IO 的附加好处：路径切换时的拥塞控制重置等逻辑完全自主——这正是 iroh 当年
  fork quinn 的原因，我们直接拥有，无需 fork。
- 密码学：`rustls-ring`（`ring` 已是仓库现有依赖，无 C 构建）。
- 远期多路径观察对象：n0-computer 的 `noq`（原生 MPQUIC），现阶段不引入（tokio-based 且年轻）。
- **保留传输层加密，不做"去加密"优化**，原因：
  1. **peer 中继的信任模型依赖它**：§4.7 规定中继节点看不见内容——这要求 E2E 加密存在。去掉后 B 转发 A↔C 的流量将是明文。
  2. **"上层都是加密的"不成立**：地基同时承载 Clash 侧的任意流量（TUN 投影），内层可能是明文 HTTP、DNS 等；传输层是唯一的加密。
  3. **QUIC 线格式与加密深度绑定**，去加密 = 深度定制 fork，维护负担大。
  4. 元数据保护（包大小/时序）对"自由"目标有意义——流量分析正是封锁手段之一。
  5. AES-GCM 硬件加速下加解密相对网络瓶颈可忽略；无实测不优化。
- 远期可选：underlay 已加密（如跑在 WireGuard 内）时的协商式跳过 AEAD，需实测驱动。

### 3.5 代理传输（P1）：节点间链路可跑在代理协议上

**问题**：mesh 节点间的直连可能被封锁（QUIC/UDP 被限、TCP 被 RST），但已有
代理（Trojan/SS 等，TLS 伪装）能通。此时节点 A 应能经代理连接到节点 B，
mesh 流量跑在代理隧道里。

**关键区分**：这是 **transport**（节点间链路怎么建），不是 §4 的"代理出口"
（流量离开 mesh 去互联网）。两者在不同层：
- 代理出口 = egress，per-flow 决策（规则引擎）
- 代理传输 = underlay，per-link 决策（路径层）

**设计**：
- quinn-proto 是 sans-IO，driver 只需要字节流。新增 `ProxyTransport`：
  先经 SOCKS5 CONNECT / shadowsocks / trojan 握手建出 TCP，再把字节流
  交给 QUIC driver。QUIC 层零改动。
- 路径层 fallback 链扩展：直连 QUIC → **经代理的 QUIC** → TURN。
- 双重加密（QUIC E2E + 代理层）是故意的：代理层提供的是混淆（抗识别），
  不是保密；E2E 加密仍是信任边界（§4.7 中继不可见内容）。
- `Transport` trait 现在就要留好扩展点，避免加时重构 driver 接口。

**真实场景**：
1. 国内↔国外节点直连被墙，Trojan 代理能通 → 经代理建 mesh 链路
2. 纯代理出口网络（如公司内网只允许 HTTP 代理）→ 代理是节点入网的唯一方式
3. 复用已有代理订阅当中继传输，不额外部署 TURN

**优先级**：P1。P0 先跑通直连 QUIC。

## 4. 路径层：智能路径管理

路径层回答一个问题：**到对端的包，现在走哪条路？**

### 4.1 候选路径（四级回退）

```
直连（NAT 穿透，UDP 打洞）
  → Mesh 转发（经其他节点多跳，FIB 选路）
  → TURN 中继（标准中继）
  → 代理出口（自由层，见 §5）
```

四级按"速度优先、成本递增"排列。直连最快最便宜；mesh 转发消耗中继节点的带宽/电量
（需 opt-in，见 §4.7）；TURN 花中继带宽；代理出口最慢但能穿封锁。

**为什么 mesh 转发不增加新机制复杂度**：A/B 层已建成 LSA 发现 + Dijkstra + FIB
（`SharedFibManager`），peer 转发就是 FIB 的下一跳选择——A 直达不了 C 时 FIB 给出
经 B 的下一跳，B 按 FIB 转发。路径层不需要为 peer 中继发明新机制，只需要把
"经 mesh 到达"作为一个候选路径。新增的只是策略面（§4.8），不是机制面。

### 4.2 探测：双轨

- **主动探测**：空闲路径定期发轻量心跳探针（类似 disco ping/pong），保持分数新鲜。
- **被动统计**：有流量时用真实 RTT/丢包/吞吐更新分数，不额外发包。
- 移动端约束：蜂窝网络下降低探测频率，感知 radio 状态（见 §10）。

### 4.3 打分

```
score = w1 * f(rtt) + w2 * f(loss) + w3 * f(throughput) - w4 * cost
```

- `cost`：TURN 中继带宽成本、代理出口延迟惩罚、蜂窝流量计费。
- 分数用 EWMA 平滑，避免单次抖动导致频繁切换。

### 4.4 竞速（Racing）

- **建连竞速**：并行尝试多条路径，先成功者胜。staggered：直连先发，~200ms 不通再起 TURN/代理。
- **适用面**：初建连、TURN 服务器之间、代理出口之间、v4/v6 之间。
- **预算**：竞速消耗额外包、唤醒 radio、产生中继计费——要有上限。

### 4.5 切换与粘性

- **切换条件**：新路径分数显著优于当前（hysteresis 门限）且持续一段时间，防抖动。
- **连接粘性**：连接级 pinning。老连接除非路径失效或严重劣化不迁移；新连接用当前最优路径。
- **抢占式迁移**：质量预测（§4.6）显示当前路径将劣化时，提前迁移。

参考：iroh 的 `BiasedRttPathSelector`（直连优先、relay 备份、v6 给 3ms 偏好、relay→直连立即切、60s 尝试升级）是极简可解释的范例。

### 4.6 线路质量预测

三层，不上 ML，先启发式：

1. **实时**：RTT/丢包/吞吐的 EWMA。
2. **趋势**：RTT 持续爬升 = 拥塞前兆，提前降权。
3. **历史**：晚高峰国际出口差等时间模式（远期）。

预测输出作为打分的输入，不是独立模块。

### 4.7 中继的信任与成本模型

| 路径 | 内容可见性 | 元数据可见性 | 成本 | 默认策略 |
|---|---|---|---|---|
| 直连 | E2E 加密 | 无第三方 | 无 | 总是可用 |
| Mesh 转发 | E2E 加密，中继节点不可见 | 中继节点可见（谁↔谁、流量大小） | 对端带宽/电量 | 桌面节点默认可做中继；移动节点默认关闭（白皮书 §14.1），充电+WiFi 时可开启 |
| TURN | E2E 加密 | TURN 运营方可见 | 中继带宽（自建则无外部成本） | 按需使用 |
| 代理出口 | E2E 到代理，代理后按协议 | 代理运营方可见 | 延迟+可能的费用 | 按策略使用 |

中继配额（远期）：每节点可配置中继带宽上限、仅中继特定对端。首期用最简规则：
开/关两档 + 移动端默认关。

### 4.8 多路径（远期）

- 首期：单活跃路径 + 快速 failover。
- 后期：包级条带——按各路径拥塞窗口加权调度，并发利用直连+TURN。
- 不一次做到完整 MPQUIC；先做"调度"，再做"聚合拥塞控制"。

## 5. 互联网策略：§11 规则引擎的作用域收缩

### 5.1 两个 policy，不是一个

| | 路径 policy（自动） | 互联网 policy（用户可配） |
|---|---|---|
| 对象 | 节点互联走哪条路 | 哪些互联网目标走代理 |
| 驱动 | 探测 + 统计（§4） | 用户规则（§11 现有能力） |
| 用户感知 | 无感 | 例外配置 |

### 5.2 结论

§11 规则引擎**保留但收缩作用域**：从"一切流量的总闸"变为"互联网出口的策略"。Clash 能力保留（规则、分组、DNS 分流），但不再跟 mesh/路径层抢决策权。

**功能上不收缩**：保持 Clash 级别的规则表达能力（domain/IP CIDR/GeoIP/rule-set/provider 等），
按用户意见"功能广泛一些"。收缩的是管辖范围，不是功能深度。

- **"自由"的判定**：默认策略（内置：GeoIP + 探测）与用户规则结合。内置策略处理"明显被墙的走代理"，用户规则处理例外。
- 节点互联流量不经过规则引擎——直连/TURN/代理三级回退由路径层全自动决策。

## 6. 投影层：系统 API 的投影

目标：**应用无需修改**，用标准 socket API，地基在底下做自由高速传输。

### 6.1 TUN 透明捕获（两阶段）

- **阶段一（L3 隧道）**：TUN 抓 IP 包，封装进 fabric 数据报，对端解封装注入 TUN。复用 P3.2 的 TUN 成果。缺点：两层拥塞控制叠加（TCP 的 + fabric 的），漫游时有顿挫（TCP 靠 RTO 恢复）。
- **阶段二（L4 中继）**：用户态协议栈在本地终结 App 的 TCP，映射为 fabric 可靠流。App 看到的 TCP 锚定在本地，物理网络变化完全不可见——"WiFi 关不断传"最平滑的实现。

阶段一先行，阶段二演进。用户态 TCP 栈用库 **`smoltcp`**（用户决策，2026-09-30）。

### 6.2 语义入口

SOCKS5 / HTTP 代理作为**显式语义入口**（§11 已有）：

- HTTP 入口知道 method/host/是否为 CONNECT——egress 侧可按 host 做智能选路（"这域名被墙走代理出口"、"内网走直连"），远期可做 GET 缓存。
- 语义信息作为元数据往下传，给路径层用（§2 的"语义标签"）。

### 6.3 进程归因与优先级

- **Linux**：新流建立时查 `/proc/net/tcp` 拿 inode → 反查 `/proc/<pid>/fd` 得进程 → 按流缓存。短连接竞态需容忍。
- **Windows**：WFP（Windows Filtering Platform），另一套实现。
- **调度**：进程名对照配置定优先级类，路径层/会话层按类排队（类似 DiffServ）。例如：文件同步高优先级、后台更新低优先级。

## 7. 插件机制

### 7.1 三个插件点

| 插件点 | 用途 | 例子 |
|---|---|---|
| 混淆传输 | 反封锁手段热插拔 | obfs4-like、TLS 伪装 |
| 路径提供方 | 自定义中继/出口 | 自建 TURN、第三方代理协议 |
| 选路策略 | 自定义路径决策 | 按时段选路、按应用选路 |

### 7.2 形态

首期：**进程内 trait + 接口版本化**。进程外（子进程 + IPC，学 Tor Pluggable Transports）是远期选项，安全隔离更好但复杂度高。

### 7.3 最强理由

GFW 会升级探测，混淆手段必须能热插拔而不动核心——直接服务于"自由"目标。这是插件机制存在的第一原因，不是通用扩展性。

## 8. 身份与发现

### 8.1 身份 = 公钥（借鉴 iroh）

- 节点身份为 ed25519 公钥（`PeerId`），自认证，无需中央 CA。
- 连接认证 = 公钥验证；中继只转发密文。
- 身份与地址解耦是漫游的基础（§3.3）。

### 8.2 发现（倾向方案，未最终定）

需求：给定 `PeerId`，找到"当前可达地址 + 归属中继"。倾向零新机制的组合：

- **LSA 携带地址**：A/B 层已有 LSA 泛洪，节点地址可随 LSA 扩散——mesh 内发现直接复用。
- **mDNS**：局域网发现。
- **静态配置**：显式地址/中继 URL。

pkarr 思想（公钥寻址的签名记录）作为远期选项。用户未最终定稿，默认按上述三项推进。

## 9. iroh 对照：设计验证

iroh（n0-computer，Rust，1.0 发布于 2026-06-15，线协议已稳定）验证了本设计的核心架构：

```
iroh                      Nexus 地基
Endpoint（按公钥 dial）  →  §3 会话层 API
iroh-quinn（QUIC）       →  §3 QUIC-like（语义对标）
MagicSock（路径复用器）   →  §4 路径层
iroh-relay（无状态中继）  →  §4 TURN 标准中继
Discovery trait          →  §8.2（待设计）
```

**可直接借鉴的思想**：

1. **单 socket 复用**：MagicSock 用 QUIC fixed bit 在同一 UDP socket 上区分 QUIC 包和打洞包——避免多 socket 打洞失效问题。
2. **极简选路**：`BiasedRttPathSelector`——简单、可解释，符合"自动化必须可解释"原则。
3. **quinn fork 的教训**：iroh fork quinn 是为了"路径切换时重置拥塞控制"——如果我们自研传输层，这个坑要预先处理。
4. **数据点**：打洞成功率 ~90%，~95% 字节走直连——三级回退中 relay 是少数情况，印证"直连优先"策略的收益。

**Nexus 的差异**（iroh 没有、我们要做的）：自由层（代理出口、混淆插件）、系统投影层（TUN、语义入口、进程 QoS）。

## 12. 实施路线（草案）

```
阶段 0（现状盘点）
  TUN（P3.2）✓ / §11 代理 ✓ / A-B 层路由（FIB/选路库）✓
  → 明确哪些现状资产直接进入地基

阶段 1：会话层骨架
  ConnectionId、加密、可靠流（单路径）、datagram、stats API
  验收：两节点经 fabric 传文件，API 按 §3.2 可用

阶段 2：路径层
  直连 → Mesh 转发（复用 A/B 层 FIB）→ TURN → 代理出口，四级回退
  探测 + 打分 + 切换 + 粘性（§4.2/4.3/4.5），暂不做竞速/预测/多路径
  验收：WiFi 关不断传（§6 场景）

阶段 3：投影层
  L3 隧道（阶段一）→ 语义入口整合 → 进程 QoS
  验收：未修改 App 走 TUN 上网，HTTP 代理按 host 选路

阶段 4：进阶
  竞速、质量预测、L4 中继、多路径、插件机制
```

每阶段独立验收，不降低门槛（vision-realignment 流程要求）。

**复杂度控制**：本文是完整蓝图，不是首期范围。P0 最小可用 = 阶段 1（会话层单路径）
+ 阶段 2（直连+TURN+基础选路，无竞速/预测/多路径）；mesh 转发复用已有 FIB，
不新增机制复杂度。阶段 4 的每一项（竞速、预测、L4 中继、多路径、插件）都可以
独立推迟而不影响 P0。真正的复杂度风险只有两处：用户态 TCP 栈（§6.1 阶段二）
和完整多路径拥塞控制（§4.8），都在远期。
