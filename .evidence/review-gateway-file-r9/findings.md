## 1. 问题 A —— 归属检查的强度到底是多少

### A(1) 同形前提由谁担保 `[读]+[核]`

**没有人担保。** 引擎对 `source` 不做解析也不做规范化：`authenticate` 原样存（`:1711`）、`close_session`
逐字比（`:1749`）、`per_browser_sessions` 逐字比（`:1692`）、`source_key` 对原文摘要（`:829-835`）。
`G16:305-309`、`PRODUCT:3333-3336`、`requirements.toml:89` 三处新句子都只说『必须出示与会话**相同**的传输地址』，
没有一句说『两处必须由同一表示供给』，也没有一句说『source 为空时怎么办』——而 `token` 空串在 `:1401` 被硬拒，
`source` 空串**没有任何校验**，本批却刚把它升格为归属证明（`succeed` doc `:1105-1106` 写『这条路从入口上就断了』）。
后果两向：(a) 合法所有者在表示变化时（重连换临时端口、一处带端口一处不带、IPv6 方括号、`%zone`）**关不掉自己的
会话** ⇒ 会话槽、它的 `.part`、它的发送预算都要等 `idle_timeout`（默认 300 s）才释放，而 `max_sessions` 默认 4 ⇒
客户端每次重连自堵一次；这是自伤不是越权，但它是**功能被关掉**。(b) 若 wire 送 `ip:port`，源限额与源锁被『每个
连接一个新键』直接豁免 ⇒ `G15:260-264` 的『一个地址 40 条 / 需要 128 个地址』两句里的『地址』退化成『字符串』。
契约里唯一登记过这个前提的是 `MODULE:325-327`，而它只挂在 **per-peer 配额**那一句上（r3 N-5）⇒ 同一把键的三种新
用法没有一种带着它。仓内没有任何测试用带端口的形态（夹具一律裸 IP，如 `10.0.0.40`）。不判 FAIL 的理由：今天
`close_session` 无任何 wire 调用者（`[核]` grep 全仓命中只有 examples/单测/文档；`src/gateway.rs` 的
`close_session_id` 属 DataChannel，与 FileEngine 无关，`MODULE:234-235` 自己也写明），且在同形前提下新检查严格更安全。
⇒ **R9-W-1**。

### A(2) 与 r8 R8-W-2 那条洞相比还剩多少 `[读]`

小得多且**已登记**：攻击者现在要同时持有 (i) 可枚举的会话号（`next_session` 从 1 起，`:1414/:1705`）与 (ii) 受害者的
传输地址字符串。`MODULE:232-233` 把残余写成『源地址是传输地址而不是凭证，同一 NAT/同一出口下能看见彼此地址的调用方
仍互相可判，凭证化等 M2 capability』✓ 准确，且 `G15:234-235` 补了『这条入口今天还没有 wire 调用者』这半句诚实边界 ✓。
没登记的是 A(1) 那一半（表示稳定性）与 §2 的 R9-W-5（同一整数猜测破坏面在 `abort_upload` 那侧原样保留）。

### A(3) `NOT_FOUND` 同形性逐格核 `[读]+[算]`

**功能面逐字同形**：两分支 `record` 的六个入参完全一致（session 同、principal 留空、root 空串、action
`close_session`、rel = `id.to_string()`、code `NOT_FOUND`）——`:1743` 对 `:1757`；只有 `:1774` 的 OK 行带真实 principal。
返回码同、消息字面量同（两处都是 `no such file session for this peer`）。审计环侧效应也同形：各 push 恰好一行 ⇒
满环时 `audit_dropped` 同样 +1（`:2668-2671`），没有挤出计数差。**回查补 principal** 只在键在表时生效
（`:2660-2664`），而外来分支的 `record` 跑在 `:1759` 的 `insert` **之前**、该键此刻已被 `:1739` 的 `remove` 取走 ⇒
补不到东西，两分支的空串一致。实现方自报『他们的测试抓过这个顺序』**复核为真能抓住**：P5（`record` 挪到 `insert`
之后）⇒ `:3707` 断言 `rec_unknown.principal == rec_foreign.principal` 左空右 `victim` ⇒ 红 ✓。
三条没登记的其它通道：(a) **时序**——外来分支多做一次变长字符串比较 + 一次 `HashMap::insert` ⇒ `close_session`
在时序上仍是存在性 oracle，而 `MODULE:225-226` 那句『所以这条入口不做会话存在性的 oracle』是**无限定**的；
(b) **比较形状**——`:1749` 用短路 `!=`，与同一份契约对令牌比较『必须常数时间』的口径不一致（那边专门开了计数钉它）；
(c) **迭代顺序**——remove+insert 同键会改变 `HashMap` 桶占用，而 `sweep_idle`（`:1779-1798`）返回按迭代序的 id 列表
⇒ 被拒的 close 可能扰动一次回收顺序（需观察者能看到回收列表才成立，M2 前不可达）。⇒ R9-N-5。

### A(4) 被拒路径把会话 `insert` 回去会不会吞会话 `[算]`

**不可能**：该键在 `:1739` 被 `remove` 取走（返回 `Some(s)` 才走到这支），此刻表内该键必然 vacant；且 `next_session`
单调自增、从不复用 id（`:1414` 初始 1、`:1704-1705` 只加不减），也不存在别的写入者能在 `remove` 与 `insert` 之间
插同一个 id（单线程、`&mut self`）⇒ `HashMap::insert` 的覆盖同键旧值语义在本路径上不可达。`[核]` 全仓再无别处向
`sessions` 插入（只有 `:1706` authenticate 与 `:1759` 这一支）。

### A(5) 改成返回 `Result` 之后有没有漏改的调用者 `[核]`

`grep close_session` 全仓（排除 `close_session_id`）：生产代码**零调用者**；examples **9** 处（`:565/:573/:581/:711/:743/:860/:890/:900/:1064`，
其中 4 处 `let _ =` 显式忽略返回、5 处 `map_err`/`expect`/入合成式处理）；src 单测 **18** 处（`:2969/:3008/:3093/:3564/:3585/:3679/:3701/:3703/:3711/:3870/:4455/:4511/:4567/:4601/:4682/:4683/:4684/:4700`，
绝大多数 `.unwrap()`，只有 `:3701/:3703/:4511` 三处 `let _ =` 是故意的——它们随后用 `audit()` 断那一行落了账）。`sweep_idle` **不**走 `close_session`（`:1779-1798` 自己做 remove + release_session
+ record）⇒ 没有『sweep_idle 里忽略 Err 就当成功』这件事；预算释放两路（`:1770/:1794`）与审计出口（`:1774/:1795`、
`MODULE:355-357` 的动词清单）都在。`let _ =` 那 4 处都在『关掉自己刚开的探针会话』语境，忽略的是**自己的**会话，
不构成误当成功。

## 2. 问题 B —— 单源限额的正确性与新引入的不对称

**(1) 聚合上界要多少地址 `[算]`**：默认参数下 `max_buckets × lockout_after / max_failures_per_source` = 5120/40 =
**128**（`MODULE:264` 的 `ceil` 式给的就是 128，不是约数）⇒ G15 那句『约 128 个不同源地址』**对**，但『约』字多余。
**(2) 多地址撒失败时限额完全失效 `[读]`**：唯一防线又回到『表满 ⇒ 溢出计数 ⇒ 全局窗口』。契约**没有说过头**——
`G15:265-269` 明写『两道门必须可区分：源限额不升级为全体 fail-closed（那是溢出计数那条大路的后果）』、场景
`:119-120` 明写『表满那条大路仍由上面的轮换地址案例证明可达』✓。说轻的是另一个数：**武装全局窗口**的成本是
`max_buckets + lockout_after` = 1029 条失败（与 `G15:240-242` 的武装成本式同源），摊到每地址 40 条 ⇒
`ceil(1029/40)` = **26 个地址**，而不是 128——也就是本批把这条大路的攻击成本从『1 个地址 × 1029 条』改成『26 个地址
× 1029 条』，**请求条数不变**。读者只看到 128 会把它当成 DoS 面门槛。⇒ R9-N-8。
**(3) 共用 `max_throttle_buckets` 的误伤 `[算]`**：源账本 1024 行 ⇒ 一个窗口里最多 1024 个**不同 source 串**在册；
账本满时陌生地址**第一条失败就被锁满一个窗口**（`:981-989`，fail-closed 不建行）。灌满账本的攻击成本 ≈ 1029 条失败
/60 s ≈ 17.2 次每秒，**低于**同一份 G15 引用的 84.4 次每秒 ⇒ 攻击者可持续维持；后果是合法新用户打错一次口令 =
60 s 出局（`unknown_address_is_locked_…` 钉的正是这个行为，但它作为**正面断言**出现，没作为代价出现）。这条既不在
G15 的『显式声明的代价（五条）』清单里，也没有期望对象。若 `source` 含临时端口（见 A(1)），1024 行账本被一个人群
或一个连接池填满是日常量级而非攻击量级 ⇒ 这条误伤从理论变现实。⇒ R9-W-2 后半 + R9-W-1。
**(4) 抖动不存在 `[算]`**：额度耗尽那次 `charge_source` 删账本行 + 插锁（`until = now + w`）；锁窗口内 `authenticate`
在 `:1644` 被 `is_locked` 的源锁分支（`:892`）短路 ⇒ `record_failure` 不被调 ⇒ 账本既不重建也不刷新；`w` 后 decay
（`:857`）丢锁 ⇒ 该地址重新从 0 攒 40 条才能再武装。长期上限 = 40/(w + 攒 40 条的时间)，即 G15:262 的 ≈ 0.67 次每秒
✓ 复算为真。『落地即续期』要求锁窗口内还能触到 `charge_source`，只能靠 `until > now` 判过期，而锁窗口内恒假 ⇒ 不能。
『期满第一条立刻再武装』要求保留 `count = 40` 的行，而本批删了 ⇒ 删行是这条理由的正确实现。⇒ R9-N-4。
**(5) 上界规则会不会拒掉合理配置 `[算]`**：规则本身**紧**且方向正确——单地址以『每个身份 `lockout_after` 条』的打法
恰好能花掉 `max_buckets × lockout_after` 条账（默认 5120；`charge_source` 跑在 `:904` 门禁与 `:926` 插入之前，
第 5120 条时源先武装），所以高于它的额度确实永远轮不到开火 = 真死配置。于是被拒的（表 4 行却给 40 条额度）不是
有意义的组合，代价只是把**静默死配置**变成**大声拒启动**，落在可用性一侧；G12:120-122 把它写成『要逼着夹具想清楚
自己测哪道门』我认同。真正的副作用是实现者要同时想两件事：4 处显式额度（examples `:511/:694/:795`、单测 `:3263/:3492`）
+ 洪水条数与额度的关系注释都写了 ✓，但单测 `:3122` 那一处同型夹具**没改**且杀伤力被静默削掉 ⇒ R9-N-1。
**(6) 新增不对称 `[读]`**：源锁表**没有插入门禁**（`:981-1003` 两支都不看 `source_locks.len()`），而 `:974-976` 的
doc 与 `MODULE:270-272` 的契约都说它受 `max_throttle_buckets` 门禁 ⇒ 一句新写的契约谎 + 零断言（全仓只有 `== 1` 的
断言）。⇒ **R9-W-2**（这是 r8 R8-W-3 的形状被复制到新表上，r8 的修法只教会了 `locked` 那张表）。

## 3. 问题 C —— 比较唯一入口与过度声明风险

`token_eq`（`:1502-1505`）把 `saturating_add(1)` 与 `constant_time_eq(...)` 焊在同一次调用里 ⇒ 计数**不能**被
『顺手 +1』糊弄：写点全仓唯一（`:1503`，字段 `:1366` 无别处赋值/重置），要 +1 就必须执行比较；而比较的语义正确性由
成功侧（`:3868` 正确令牌恰好 +1 且放行）与拒绝侧（`:3856` 错令牌 +1 且被拒）两根断言各自钉住 ⇒ 把比较换成恒真/恒假
都会红在别的测试上。**测不到的那一半**是实现方自己已公开更正的：把 `constant_time_eq` 换成长度相关的 `!=` 零红
（`[读]` 核：`constant_time_eq` 自己的单测只测函数本体，无调用点断言），三处措辞（doc `:1498-1501`、G15 代价 (5)
`:278-287`、`REQ-010:89` 的『计数可证：可比较的尝试恰好 +1，锁定/源锁短路的尝试 +0』）逐句读下来**都站得住**，
没有一处把计数当时序证明 ✓ 实现方的自我更正到位。两点要补的射程（R9-N-6）：
(1)『绕开就编不过』的机制我静态核到三个前提——`Cargo.toml:74-75` `[workspace.lints.rust] warnings = "deny"`、
`crates/nexus-web-gateway/Cargo.toml:9-10` `[lints] workspace = true`、`file_service.rs` 内零处 `allow(dead_code)`
（`:3666/:3712` 的两个 `expect` 是字符串不是属性）、`token_eq` 唯一调用点 `:1652` ⇒ 替换调用点后确为 unused；
但**编译失败与 error 文本是实现方自报、本评审未复现**。且 `cargo test --lib` 会把 `#[cfg(test)]` 里的引用算作使用
⇒ 若将来为让测试直接调 `token_eq` 留一处引用，build/clippy 仍红而 test 门不再红；同理 authenticate **之外**新增的
第二个比较点不触发 dead-code，也不被 `:3841` 看到 ⇒ 『唯一入口』目前只约束当前这一处调用点。
(2) `:1492-1496` 那句『routing the comparison through anything else … goes red』与同批正文的分层（构建期挡住 vs
测试挡住）措辞不完全一致，实际后果是编译失败而不是测试红。
**C(3) 计数与审计的耦合**：不存在假绿——被锁定短路的尝试**仍然落审计行**（`:1645`：principal 非空、session 0、
code `THROTTLED`），但计数不 +1（短路在 `:1652` 之前）⇒ `token_comparisons_short_circuit_when_locked` 的
『+0』与『仍有一行 THROTTLED 审计』是两件事，测试只断前者，后者是 G21 的既有性质，无耦合。
