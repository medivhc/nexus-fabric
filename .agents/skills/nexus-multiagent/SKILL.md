# nexus-multiagent

多个 Agent 同时向 Nexus 仓库推送代码时的协作规范。目标：并行提速，但不丢代码、不污染构建、不绕过门禁、不削弱独立评审。

**本 skill 是编排层补充。** 仓库级的机器化约定以 `AGENTS.md §29 多 Agent 协作约定` 为准（crate 归属表、NEXUS_AGENT 证据命名空间、nexus-sync 同步流程、worktree 布局），本 skill 不重复、不覆盖，只补充 §29 未涉及的编排内容：角色分工、评审配对、模型差异的任务分配。

## 使用场景

- 2 个以上 Agent 需要同时向同一仓库贡献代码。
- 各 Agent 使用不同的 Harness / Model，能力与盲区不同。
- 任务可切分为相对独立的子任务。

## 不要使用

- 单 Agent 任务（直接按 nexus-task 流程走）。
- 子任务之间文件高度交叉、无法隔离时——先重构切分，或改为串行。
- 只读分析类任务（不需要分支与合并流程）。

## 角色

- **协调者（1 个）**：拆任务、冻结契约、分配 worktree 与分支、排合并顺序、解决合并冲突、汇总报告。不直接写大块实现代码。
- **执行者（N 个）**：在自己的 worktree 里实现，只推自己的分支，提交结构化完成报告（改了什么、测试结果、commit hash）。

## 开工前（协调者）

1. **契约冻结**：按 `nexus-contract-first` 把接口契约先定死。所有执行者面对的是同一份契约，而不是彼此变动中的代码。
2. **任务切分**：保证子任务**无交叉文件**。实在交叉的，改为串行——后者 rebase 前者的分支。
3. **环境隔离**：从同一 base commit 给每个执行者建独立 worktree + 独立分支（`track/<agent>-<任务>`），独立 `CARGO_TARGET_DIR`，共用 sccache 做编译去重。每个执行者设置唯一的 `NEXUS_AGENT` 身份值（`[A-Za-z0-9_-]`，≤32 字符，并发时不撞名；长期协作建议固定，见 AGENTS.md §29.2），证据目录按 `verify-<agent>-<hash>` / `review-<scope>-<agent>-r<n>` 命名，互不覆盖、互不误标 STALE。
   - 教训（2026-09-30）：多个 Agent 共享同一 worktree 时，一个 Agent 的 `git checkout` 会 wipe 掉另一个 Agent 的未提交代码。只有已 push 的 commit 能幸存。

## 执行中

4. **分支纪律**：执行者只推自己的分支，**绝不直接推 master**。本地必须跑过 `verify --fast`（沙盒）或等价门禁再提交。
5. **交叉评审配对**：实现者与评审者永远不是同一个 Agent，评审轮换：
   - A 实现 → B 评审，B 实现 → C 评审，C 实现 → A 评审。
   - 尽量让评审者与实现者**不是同一个 Model**——不同 Model 的盲区不同，交叉评审更接近真正的"独立"。
   - 遵循 `nexus-review` 的独立性规则与八个检查维度。
6. **Verdict 门槛**：只有 APPROVED / COMMENTED 能进合并队列；CHANGES_REQUESTED 打回原实现者修复，不得进入合并。
7. **自修复循环**：执行者验证失败且判定为 Implementation Failure 时，按 `nexus-selfrepair`
   的有界循环执行（最多 3 轮、每轮换修复策略、同一失败签名第二次出现即结构化升级）。
   不得无限重试，不得为变绿而改 `scenarios/` 断言；循环终点是独立评审，不是合并。
8. **完成报告附人工插手清单**：执行者提交结构化完成报告时，必须附上 `nexus-task` step 10 格式的「人工插手清单」——记录本子任务中人类介入的每一项（人工纠正 / 重讲背景 / 工具转述 / 手动验证），只记真实发生的。

## 合并（协调者串行执行）

8. **一次合一个**：取分支 → 按 AGENTS.md §29.3 的 `nexus-sync` 流程（fetch → rebase 到最新 master → verify --fast → push）。绝不让两个执行者同时推 master。冲突只在同步时刻暴露并显式解决（§17：FF/3-way/显式冲突，已提交数据不静默丢弃）。
9. **冲突由协调者解**：不丢给执行者，避免各说各话。
10. **门禁不可绕过**：任何情况下不得使用 `--no-verify` 或等价手段。门禁 FAIL 先读完整输出、定位真因、修复——合法的 FAIL 不是 hook hang。
11. **人工插手清单的汇总与固化**（协调者）：任务全部合并完成后，把各执行者完成报告里的人工插手清单汇总写入 `.agents/knowledge/entries/YYYY-MM-DD-intervention-<任务>.md`（buffer，按 §19.2 条目格式附原因分类）。协调者定期扫描 buffer：同一类人工插手在 3 个以上任务中重复出现 → 提议固化为 skill 条目或 lint 规则，走正常技能变更流程（同步 + md5 对账）落地。

## 模型差异的任务分配

- **实现速度快的 Model**：体力型任务（批量测试、脚手架、重复性迁移）。
- **推理强的 Model**：评审与契约设计。评审质量直接决定这套流程的价值，好钢用在刀刃上。
- **双 Model 择优**（奢侈品，留给关键任务）：同一任务两个 Model 各做一遍，协调者按评审结论择优组合。N2 P1 的 21 项 P1 就是这么成的，效果好但成本高。

## 铁律

1. **不共享 worktree**——并行轨道从开始就各用独立 worktree。
2. **不直接推 master**——所有代码走分支 + 协调者串行合并。
3. **不 `--no-verify`**——门禁是协议，不是建议。
4. **实现 ≠ 评审**——用户铁律（2026-10-05）："以后都需要独立 review 然后修复"。任何实现完成后，必须经独立评审、修复发现的问题，才能算完成。
