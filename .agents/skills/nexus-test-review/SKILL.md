# nexus-test-review — TDD 测试用例独立评审

TDD 的第一张判卷标准是测试用例本身。测试错了，后面全错。本技能定义测试用例写完后、实现开始前的独立评审。

## 使用场景

- `nexus-task` 流程第 3.5 步：测试用例写完，等待评审冻结。
- 任何 TDD 流程中需要确认"测试本身是对的"的环节。

## 不要使用

- 测试已经过实现验证后（那是回归测试，不是评审对象）。
- 非 TDD 流程（测试后补的场景不适用本技能）。

## 独立性机制（子代理）

独立评审必须通过子代理实现，满足以下四条（所有 harness 通用：opencode Task、Claude Code Subagent、Cursor 等）：

1. **干净上下文**：子代理的输入只能是：契约/spec + 待评审的测试文件 + 本 skill 的评审标准。禁止传入测试编写者的会话历史、思考过程、草稿。
2. **单向信息流**：编写者 → 子代理（只给材料），子代理 → 编写者（只给 verdict + findings）。子代理不许反问编写者要上下文，缺信息就判 CHANGES_REQUESTED 并注明缺什么。
3. **盲评**：子代理不知道测试是谁写的，也不知道实现是谁做的。
4. **证据**：子代理的完整输出存入 `.evidence/test-review-<id>/`，包括输入材料清单（证明没塞私货）。

## 评审维度

### 1. 覆盖度
- 每个 AC/契约点都有对应的测试吗？
- 有没有漏掉的契约分支？

### 2. 有效性（最重要）
- 测试真的会失败吗？空断言、恒真条件是最常见的坏测试。
- 每个测试至少能说出一种让它失败的实现错误。

### 3. 独立性
- 测试是否依赖实现细节？换一种合法实现方式，测试还过吗？
- **铁律：测试的期望值只能来自契约/AC，禁止照着实现行为抄。** 发现期望值是运行实现后填的，直接判 CHANGES_REQUESTED。

### 4. 边界
- 空输入、极大值、错误路径、并发场景覆盖了吗？
- 超时、取消、资源耗尽这些非 happy path 有吗？

### 5. 可读性
- 测试名能说清在测什么吗？
- 失败时能定位到哪个契约点吗？

## 双错处理（测试与实现都有问题）

根因：测试和实现是同一个错误心智模型写出来的，会互相印证。处理流程：

1. **先冻结**：停下，不许两边同时改（同时改就是在猜）。
2. **回到契约**：重读 spec 相关 AC，确认"应该是什么行为"。
3. **先修测试设计**：按契约重写测试期望值，重新走本技能评审。
4. **再修实现**：让正确的测试去驱动。
5. **分不清哪边错时**：用变异测试——故意把实现改坏，看测试能不能抓出来。抓不出说明测试本身是空的，先修测试。

**禁止双向调和**：永远不许"改测试去迎合实现"，也不许"改实现去迎合测试"。两边各自独立对契约。

## 输出格式

```markdown
# Test Review <id>

## Verdict
APPROVED / CHANGES_REQUESTED

## Findings
- [维度] 文件:行号 — 问题描述 — 建议

## 输入材料清单
- 契约/spec：<路径>
- 测试文件：<路径>
- 评审标准版本：nexus-test-review <date>
```

## 输入

- 契约/spec（冻结版本）。
- 待评审的测试文件（必须已写完、未开始实现）。

## 输出

- 评审报告（见上），存入 `.evidence/test-review-<id>/`。
- Verdict=APPROVED → 测试用例冻结，进入实现。
- Verdict=CHANGES_REQUESTED → 打回重写测试，不进入实现。
