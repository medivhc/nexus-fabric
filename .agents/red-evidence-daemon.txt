# Red Evidence —— Provider Daemon 与结果缓存（契约先行的红灯确认，实现开始前）

宿主：Windows（冒烟宿主），rustc 1.95.0，rev `9c672a7` 之上的工作树（契约文件已写、实现未动）。
可执行文件：`./target/debug/nexus-harness.exe`（`daemon` 子命令**不存在**）。
流程依据：`.agents/skills/nexus-test-review/SKILL.md` 的"红灯确认"——测试必须可运行且处于失败态，
不是"看起来对"；本文件就是那条红灯的载体（场景 `.toml` 是本模块的测试用例形态）。

## R0 直接调用 daemon 命令面：能力缺席，且是 fail-closed 的缺席

    nexus-harness daemon selftest --json   exit=2  {"command":"daemon","schema_version":1,
      "verdict":"BLOCKED","message":"supported commands: status, context, check, test,
      verify, explain, bench, replay, scenario, code"}
    nexus-harness daemon status --json     exit=2  同上
    nexus-harness daemon start --json      exit=2  同上

三条都是 `BLOCKED` + 退出码 2：**没有**假装成功、**没有**空输出、也**没有**默默去跑别的命令。
顺带记一处将在实现时一并修正的口径：这条兜底消息里的命令清单本身还不含 `daemon`
（`main.rs` 的 `_` 分支硬编码），实现时若不同步更新，就会出现"命令存在但帮助说它不存在"。

    evidence_id = scenario-fcd8f6fb1e53   failed_step = "expect"

另记一次自己的错并说明它为什么值得留在红灯档案里：第一次跑这条场景时我按**文件名**猜场景 id

`failed_step="lookup"`）。那不算红灯，只是我没按文件里声明的 `id` 引用。已把 id 统一成

## 这四条红灯共同说明什么

- 红灯发生在 `failed_step="expect"` 而非 `"parse"`/`"run"`/`"lookup"` ⇒ 场景文件本身可解析、
  命令可执行，失败原因纯粹是"被测能力不存在"。这是 nexus-test-review 要的红灯形态。
- 覆盖分工是按"能不能确定化"划的，不是随手分的：
  ① 能由单条命令确定观察的性质 → 独立场景：`daemon-explicit-only`（不问 daemon 的形状）、
     `cache-disabled`（关掉缓存的形状）、`daemon-command-surface`（未知命令的形状）、
     `daemon-lifecycle`（selftest 的整体形状）；
  ② 需要**控制状态**才可确定的（start 幂等、第二个进程是否真复用、stale 租约回落、
     digest 变更后不冒充新鲜、缓存键绑定、线协议越权拒绝、stop 后零会话零残留）
     → 落在 `daemon selftest` 的 13 条探针里，由场景断言 `probe_count=13` 与
     `probes_all_ok=true` 再整体钉住。理由：这些性质依赖"先有一个 daemon / 先改掉工作树 /
     先杀进程"，放在普通场景里会变成依赖环境、别人一跑就假绿或假红的测试。
- 仍然承认的覆盖缺口（评审时请重点看这几处）：结果层缓存的**收益**没有场景证据（§4 已声明
  它只钉结构、不钉时延）；`--max-workspaces` 的 LRU 驱逐只由 selftest 的一条探针负责；
  跨宿主差异（Windows 的 temp ACL、Linux 的 socket 语义）只有 `daemon-lifecycle` 一条间接覆盖。

## 第三轮红灯（盲评 round 2 打回后的第二次修订；4 条阻塞 + 若干 nit）

round-2 案卷 `.evidence/test-review-branch-feature-code-intel-phase-234-2026-10-12-r2/`：

四条阻塞与处置
1. **命名空间必须每次运行唯一**（不只是"私有"）：否则第二次跑会命中上一次的缓存条目，
   `default_path_*` 与 `cache_second_run_tier` 的含义随运行次数漂移。契约「作用域与隔离」②已改写。
2. **缓存命中时返回什么，契约一字未写** —— 这条最狠：命中若跳过 provider，已冻结的 16 条
   `code_*` 场景（如 `code_intelligence_symbol.toml:31` 钉 `provider.kind`）就会变红，
   实现方会被冻结测试绑架 —— 正是技能禁止的双向调和。已规定：命中 = **逐字回放**录得的
   envelope（含 `provider`/`snapshot`/`budget`），`cache.tier` 属**追加**字段而非替换，
   命中前仍与当前工作树指纹比对、前后 digest 检查不放宽。
3. **`daemon.running` 在 `--no-daemon` 下两义合法**（"本次经由 daemon" vs "机器上有 daemon"），
   而 explicit-only 钉 `false` 就成了碰运气。已把语义钉死为前者，另设 `daemon.detected`
   暴露"有没有可用 daemon"，两问分离。
4. **`daemon *` 输出的可得性锚点缺失**（`command="daemon"`、`authority`、`snapshot` 在
   BLOCKED/selftest 路径上没有条款要求）。已补"所有 daemon 输出都带这三项"。

一并收掉的 nit：契约里"真卡住以 `failed_step="run"` 暴露"是**错的**（求值器词表是
`lookup`/`fixture`/`command`/`parse`/`expect`，没有 `run`）⇒ 改成 `command`；
提交说明声称已补"未运行时 port/pid/lease_path 不出现"但清单里根本没有对应探针 ⇒

## 第四轮红灯与裁决记录（盲评 round 3 推翻了我上一轮两处修法）

round-3 案卷 `.evidence/test-review-branch-feature-code-intel-phase-234-2026-10-12-r3/`：
verdict 仍 `CHANGES_REQUESTED`，4 条阻塞，且明确指出 r2 那 4 条只 **2 CLOSED / 2 PARTIAL**。
三条最关键的不是"写得不够"，而是**与我自己的其他规则或系统里的冻结约束互相矛盾**：

1. **"逐字回放" 与 "缓存不得含源码原文" 没有共同解** —— `results.0.snippet` 就是源码行，
   而 `hover` / `diagnostics_item_shape` 两条**已冻结**场景钉它非空。
   裁决：**含源码文本的 verb（hover/diagnostics）不入结果层缓存**，而不是去动冻结期望，
   也不是放宽"不含源码"。
2. **"不刷新任何字段" 撞上绑定与计数不变量** —— `working_tree_digest` 既不看提交历史也不看
   工具链版本，空提交或 rustc 升级都不改它 ⇒ 连 `snapshot.source_revision` 一起回放就是
   拿过期绑定冒充新鲜。裁决：字段分两类，**语义事实逐字回放、运行元数据一律按本次运行生成**
   （`snapshot.*` revision/toolchain、`provider.duration_ms`/`session_*`、`daemon.*`、`cache.*`）。
3. **缓存键不含策略位 ⇒ 回放串味** —— `code symbol` 与 `code symbol --no-daemon` 同键，
   命中会把上一次的 `daemon.running` 带回来，本轮新场景自己变环境依赖红。裁决：键加策略位。
4. **`mcp selftest --with-query` 落在缓存作用域内 ⇒ 新假绿通道**：第二次查询可由回放满足，
   Phase 4 的复用判据（`session_reused`/`session_queries`）被我自己造的缓存糊过去。
   裁决：**两个 selftest 的复用类探针强制不读不写缓存**（硬性排除，写进契约）。
5. **我上轮加的"复制成 temp scratch"直接违反冻结的作用域不变量** —— `--workspace` 归一化后
   必须在仓库内（越界 ⇒ `WORKSPACE_UNRESOLVED`），仓库外副本让 `verdict="PASS"` 永不可达；
   仓库内可写副本又与 `dirty_after_lifecycle=0` 与并行调度冲突（会把别的 `code_*` 打成 STALE）。
   裁决：撤掉复制规则，selftest 对仓库内夹具**只读不写**；`digest_invalidation_reason` 从清单
   移除，改由点名单测承载（观测指纹变更必然要求真改工作树，与"不写仓库"互斥）。

同时按它"契约被写胖了吗"的质疑撤下 9 项（32 → **23**）：4 项关于自身输出形状的布尔
（字段缺席、原因非空、等式成立、有界且不含源码）改为**点名单测**——求值器根本没有"缺席"算子，
房内先例（`workspace_escape.toml:44-47` 点名 `workspace_escape_is_rejected_before_provider_spawn`）
就是这么分的；线协议/单端口拓扑两项撤回实现细节定位（契约自己说线协议是实现细节，就不该同时
钉进对外清单）；`reuse_queries_total=2` 钉的是 selftest 脚本步长，撤；`max_workspaces=2` 属宿主
调优不作兼容承诺；`cache.tier` 词表去掉 `memory`（会话内重复由 `provider.session_reused` 表达，
两个观测点不得互相冒充）。另撤掉 `daemon-status-defaults` 场景本身：契约没写"检测到 daemon 时
报默认值还是生效值"、也没定义不带 `--workspace` 探测哪个命名空间 ⇒ 期望值来源不在契约内。
`probe_count` 不再由散文担保：改由单测 `daemon_selftest_field_list_matches_contract` 解析本文件
清单块与实际键集合逐名对齐（多一名少一名都红），三处手写数字的耦合解开。
